The read-only principle: why your AI agent should read, not write

Founder notes · Manu Parasuraman

Everyone is connecting agents to their tools. Almost nobody is asking the first question that matters: should this agent be able to change things?

Write access is where the risk lives

A read-only agent can only waste your time. A write-enabled agent can waste your data. When you give an assistant permission to edit, delete, or reorganize, every hallucination becomes an irreversible action. Read access gives you ninety percent of the value with a fraction of the blast radius: the agent can ground its answers in your real context, but it cannot act on a mistake.

How ORANO implements it

ORANO exposes a personal MCP server that is read-focused by design. Your agent — ChatGPT, Claude, Cursor, anything MCP-compatible — can list your projects, read a project's summary, tasks and sources, search your library, and read your curated memory facts. It cannot mutate projects, tasks, or memory. Access is per-person API keys with a required scope (orano:read), rate-limited at 240 calls per user per 60 minutes, with up to 10 active keys.

The machine-readable details are public: oranoai.com/mcp.json.

Honest limits

  • Provisioning currently requires a paid subscription and a manually generated key — no one-click OAuth yet.
  • The only write-side state change is acknowledging a handoff you explicitly triggered from the app.
  • Write actions remain a roadmap item, gated behind the same scope system.

Start read-only. Earn write access later.
